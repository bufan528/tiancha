## 0. 天查是什么

**天查是一个能够长期积累「专业投资知识」与「行业知识」，并用这两个知识体系持续规划、执行、复盘、优化投资研究的 Agent。**

它不是 PDF 分析器、不是 RAG、不是报告生成器、不是公司推荐器、不是研究任务管理器、不是评分器。这些都是它的**能力**，不是它的**本质**。

它的本质是一个**学习回路**：

```
知识 → 研究 → 新知识 → 方法论进化 → 更好的研究 → 更多新知识 → …
```

判据只有一条：**用得越久，它研究一个行业的速度、深度、判断准确度是否在提升？**
如果答案是"不提升"，那天查只是个流程工具，无论表建得多整齐。

## A. 两个知识体系

### A.1 专业投资知识体系（Investment Methodology Knowledge）

**回答的问题**：「一个专业投资人**应该如何**研究一个行业、判断一个行业、判断一家企业？」

**它沉淀什么**（这是它的范围，不是字段）：

| 类别 | 例 |
|---|---|
| 研究/拆解方法 | 一个行业该怎么拆？按什么维度切？ |
| 产业链分析方法 | 为什么要看产业链？看产业链的什么？ |
| 行业类型差异 | 制造业 / 服务业 / 平台 / 硬科技 各自该重点看什么 |
| 问题→信息映射 | 「判断需求真实性」应该去找什么信息？ |
| 证据→判断映射 | 什么证据才能支撑「技术壁垒高」这个判断？ |
| 潜力判断 | 如何判断行业的发展潜力 |
| 竞争力判断 | 如何判断企业竞争力 |
| 风险识别 | 如何识别致命风险 |
| 误导识别 | 哪些信息容易误导投资判断（口径、幸存者偏差、卖方立场） |
| 成功经验 | 历史上哪些研究路径有效 |
| 失败经验 | 历史上哪些判断被推翻，为什么 |
| 方法不适用 | 用户实际调研后发现原方法哪里不适用 |
| 方法修正 | 新资料 / 新案例 / 新反例对原方法的修正 |

**它如何产生**：初始是一份 **Human-approved baseline**（当前是 12 维研究框架）。
**它如何更新**：**只能**通过 `研究经验 → 方法论修订提案 → 人工确认 → 新版本`。模型永不自动改。
**它的形态**：不是"12 个维度的固定清单"，而是 **「维度 + 判据 + 行业类型差异 + 权重/优先级」的版本化知识体**。12 维只是 v1 的起点。

> **关键**：它包含"**对不同类型行业，重点应该不同**"这类知识。例如"在平台型行业，[[网络效应]] 比 [[毛利率]] 更能预测胜负"——这正是它必须能进化的原因。

### A.2 行业研究知识体系（Industry Research Knowledge）

**回答的问题**：「**这个**具体行业（如 AI Agent）到底是什么情况？」

**它沉淀什么**：

- 行业结构、产业链与各环节角色
- 上游 / 核心企业 / 下游 / 客户 / 渠道 / 服务商
- 竞争格局（龙头 / 第二梯队 / 新进入者 / 替代者）
- 商业模式（收入模式 / 付费方式 / 毛利 / 获客 / 续费）
- 技术路线与迭代
- 市场空间与增速（**含不同口径**）
- 关键变量、关键企业
- 专家观点、咨询机构观点（**可相互矛盾**）
- 政策、最新事件、历史变化

**它如何产生**：由 **Evidence / Claim 投影**而成（不是手写文档）。
**它如何更新**：新资料 → 断言 → 与已有认知比较（支持 / 修正 / 冲突 / 取代）。
**它的形态**：**每个行业一套**，随研究不断加深。

### A.3 两个体系如何互相影响（这是核心，不是两个平行库）

**正向：投资方法论 → 行业研究**

```
专业投资知识（该怎么研究）
   ↓ 生成研究框架与信息需求
行业研究（这个行业要查什么）
   ↓ 收集证据
Evidence / Claim
   ↓ 投影
行业知识（这个行业现在是什么情况）
```

**反向：行业研究 → 投资方法论**（← **此前被我错误地放到了很后面**）

```
行业知识（这个行业出现了新事实/新案例/新反例）
   ↓ 提炼
研究经验（关于"如何研究"的经验，而非"这个行业"的知识）
   ↓ 累积成模式
方法论修订提案（Methodology Candidate）
   ↓
人工确认（Human Gate）
   ↓
新的投资方法论（新版本，旧版本保留）
```

**举例**（用户给的例子，我按模型展开）：

```
原方法论：判断某类行业，重点观察 A、B、C
    ↓
天查研究了 20 个此类行业
    ↓
行业知识层出现反复出现的信号：
    "在这类行业里，A 与最终结果的相关性很低，D 反而每次都关键"
    ↓
研究经验：对"这类行业"，v1 方法论的权重分配失效
    ↓
方法论修订提案：针对「该类行业」增加 D、降低 A 的权重
    ↓
人工确认 → Methodology v2（旧 v1 保留，历史评估仍可回溯到 v1）
```

**要点**：这次研究**不只更新行业知识，还产生了一条针对方法论的经验**。这就是"越研究越懂投资"。

### A.4 为什么这是天查的命门

- 只有 A.2（行业知识）→ 天查是个**越用越厚的资料库**，但它判断行业的方式永远停在起点。
- 只有 A.1（方法论）→ 天查是个**静态的行业分析模板**。
- **两者协同** → 天查才是一个会**自我改进研究方法**的研究者。

因此：**方法论进化不是"最后的锦上添花"，而是与外层研究同步生长的一等闭环**（Phase 排布见 §H）。

## B. 信息与认知的分层（Information Pool 的重新定义）

> 本轮最重要的纠正：**Information Pool 不是覆盖度状态表，它是「结构化信息框架 + 已掌握的信息内容」。**

### B.1 五层，各回答一个问题

| 层 | 回答的问题 | 归属体系 | 一句话 |
|---|---|---|---|
| **方法论维度** Dimension | 「应该看哪些方面」 | 投资知识 | 框架 |
| **信息需求** Requirement | 「这个维度上，我们需要知道什么」 | 投资知识 → 行业研究 | 问题式需求 |
| **信息槽位** Slot（Information Pool 的单元） | 「这个维度上，我们**目前具体知道了什么**」 | 行业研究 | 框架 + 内容 |
| **断言/证据** Claim / Evidence | 「谁、在什么材料里、说了什么」 | 事实层（Source of Truth） | 原子事实 |
| **认知** Knowledge | 「据此，我们形成了什么**更高层次的判断**」 | 行业研究（认知） | 判断 |

### B.2 一个完整例子（用户给的例子，展开成模型）

```
【方法论维度】市场空间
      ↓
【信息需求】市场规模是多少？增长速度是多少？
      ↓
【信息槽位】市场空间槽位 —— 目前掌握的具体信息：
      ├─ 条目1：2025 年 ≈ 500 亿元（来源：券商 A 报告，口径：含硬件）
      ├─ 条目2：2025 年 ≈ 320 亿元（来源：咨询 B，口径：仅软件）
      ├─ 条目3：2030 年预测 2000 亿元（来源：券商 C，口径：含硬件）
      └─ 该槽位状态：口径不一致 → 部分满足（尚未达到"可溯源 + 结构拆分"的确认条件）
      ↓
【断言/证据】每条条目背后都有 Claim + Evidence + 原始材料
      ↓
【认知】"市场正在高速增长，但统计口径存在明显差异，需统一口径后重估"
```

**注意三者的差别**：
- 需求问的是「**要什么**」；
- 槽位装的是「**现在有什么**」（含多来源、多口径、互相矛盾的具体信息）；
- 认知是「**我们下什么判断**」。

### B.3 信息槽位必须承载信息内容（不是状态）

槽位里装的是一条条**信息条目**，每条至少能说清：

- 内容（数值 / 陈述）
- 来源与出处
- **口径**（怎么算的、含什么不含什么）
- 时间（as-of）
- 指向的断言 / 证据
- 与其他条目的关系（一致 / 口径不同 / 矛盾 / 互补）

槽位同时有一个**覆盖判定**（依据方法论的确认条件）：尚无信息 / 部分掌握 / 足够确认 / 存在未解冲突。

> **这就是用户说的"同一个信息维护，获得了新的口径，就要跟老的口径做比较分析"** —— 口径比较发生在**槽位内部**（条目之间），而不是在文档里手工 diff。
>
> 同时它**不是**"巨大的无结构资料仓库"：每个条目必须挂在**某个槽位**上，而槽位由方法论维度派生。**没有槽位的信息存放地点，说明方法论还没定义好该看什么** —— 这本身就是一个应该被记录的经验信号（见 §F）。

### B.4 Pool 与 Knowledge、与 Claim 的边界（一张表定死）

| | 信息槽位（Pool） | 认知（Knowledge） | 断言（Claim/Evidence） |
|---|---|---|---|
| 单位 | 维度下的槽位 + 条目 | 一条判断 | 一条断言 |
| 内容 | **具体信息**（多来源/多口径） | **解释与结论** | 事实与出处 |
| 是否可矛盾 | 是（条目间可矛盾，并列保留） | 是（认知间可冲突，并列保留） | 是 |
| 是否 SoT | 否（是可重建的汇聚视图） | 否（是认知层） | **是** |
| 能否直接回答用户 | 否 | 是（作为判断依据） | 否 |

**一句话**：`槽位 = 把散落的断言，按"该看什么"整理成"现在知道什么"；认知 = 对整理结果下判断。`

## C. Research Strategy（研究策略）

> 用户纠正的关键：**ResearchChain 不是枚举、也不是自由标签，而是"行业研究观察结构"**；ResearchTarget 不是"推荐公司"，而是"**最能回答问题**的信息源"。

### C.1 关系总览

```
Research Question（要回答什么）
   ↓
Information Requirement（回答它需要什么信息）
   ↓
【方法论提供】为什么要看产业链 / 看产业链的什么   ← 投资知识体系
   ↓
【行业知识提供】这个行业具体有哪些关键角色/位置    ← 行业研究体系
   ↓
Research Chain（这个行业的"观察结构"：一组观察位置 + 它们的关系）
   ↓
Research Position（观察位置 / 角色，如"下游头部客户"）
   ↓
Research Target（该位置上的**具体**可访问对象，如"某客户 A"）
   ↓
QuestionTargetFit（该对象对这些问题能答多好）
   ↓
（若无最佳对象能触达 → Fallback，显式标注）
   ↓
Diligence Preparation（针对性调研准备）
```

### C.2 ResearchChain = 行业研究观察结构

**它回答**：「**这个行业，应该从哪些位置观察，才能研究清楚？**」

- 一个制造业行业可能是：原材料 → 核心零部件 → 设备 → 制造商 → 渠道 → 终端客户
- 一个服务业行业可能是：资源方 → 平台 → 服务提供商 → 客户
- AI 行业可能是：算力 → 基础模型 → Agent/应用 → 开发平台 → 企业客户 → 终端用户

**它不是固定枚举，也不是自由标签，而是三层知识的交汇结果**：

```
【方法论】"为什么必须看产业链"、"看产业链的什么"（如：看利润分配、看议价权、看瓶颈环节）
   +
【行业知识】"这个行业实际有哪些角色、谁依赖谁"（如：AI 里模型层与算力层的关系）
   ↓
  Research Chain（该行业的观察结构）
```

**每个观察位置（Research Position）必须能回答**：

1. 为什么这个位置对**当前研究**重要？
2. 它能回答哪些研究问题？
3. 它能满足哪些信息需求？
4. 它适合提供哪一类信息/证据？
5. 它有什么局限（视角偏、只会说自己的好、不懂上游成本）？

**关键**：位置是**类型级**（"下游头部客户"），对象是**实例级**（"客户 A"）。区分二者，才能既有结构、又落到具体人/公司。

### C.3 QuestionTargetFit（问题 × 对象的适配）

**它回答**：「**这家对象，对这个问题，能答得多好？为什么？哪里答不了？**」

- 适配结论：强 / 中 / 弱 / 无
- 适配理由（如：该企业处于下游核心客户位置，直接感知需求变化）
- 判断依据（链位置、经营情况、既往材料）
- 局限（它只了解自己那一段）
- 优先级（结合问题本身的重要性）

### C.4 Fallback 是正常情况，不是异常（用户的明确要求）

```
最佳对象 A（适配强）联系不上
   ↓
改选 B（适配中/弱）
   ↓ 但问题重要性 = 关键
仍进入调研提纲
   ↓
报告与提纲中**显式标注**：
"该信息来源非最佳来源，回答能力弱于 A（弱在哪里），结论需交叉验证"
```

**三条纪律**：
1. Fallback 决策必须**落库**，不能是 prompt 里的临时判断；
2. **必须说清"为什么从 A 换成 B"** 以及 "B 弱在哪里"；
3. **禁止**把 fallback 伪装成最佳（与既有设计原则一致）。

### C.5 Diligence Preparation（针对性调研准备）

**输出**：调研目的 / 当前认知 / 为何选该对象 / 对象简介与链条位置 / 它**能**回答什么 / 它**不能**回答什么 / 缺口 / 核心验证问题 / 行业层问题 / 公司层问题 / 个性化问题 / 可能追问 / 需索取的材料 / 注意事项与风险。

**两条硬约束**：
1. **每条提纲问题必须能说明"为什么问它"**（来自哪个信息需求、哪条适配判断）；
2. **禁止通用模板**（同一个对象换成任何人都不变的那种提纲，等于没做研究）。

## D. Research Target：不同的调研对象如何统一

> 用户纠正：**ResearchTarget ≠ Company**。Company 只是其中一种。

### D.1 本质定义

**ResearchTarget = 一个可被选择、可被访问、可被引用，并能提供某类信息的研究对象。**

它统一的是「**信息提供能力**」，**不是**统一的数据字段。

### D.2 类型谱系（给谱系，不穷举）

| 谱系 | 例 |
|---|---|
| **组织型** | 核心企业 / 上游企业 / 下游企业 / 客户 / 供应商 / 渠道商 / 贸易商 / 服务商 / **咨询机构** / **行业协会** / 研究机构 / 投资机构 / 政府或公共机构 |
| **个人型** | **专家** / 从业者 / 客户决策人 / 离职员工 |
| **抽象型（未来）** | 某个产品 / 某个项目 / 某个具体市场 / 某个匿名客户群体 / 某类专家群体 |

### D.3 统一抽象与差异化扩展

**所有类型共享的**（统一抽象的骨架）：

- 身份与类型
- 它在**观察结构**中的位置（Research Position）
- 它能提供的**信息类别**（与信息需求挂钩）
- **可访问性**（能约到吗）
- **局限**（它答不了什么）
- 与具体问题的**适配**（QuestionTargetFit）

**类型特有的**（差异化扩展，按需生长，不预先定死）：

- 企业 → 经营情况、产品、财务、竞争位置
- 专家 → 专长领域、独立性、立场
- 咨询机构 → 覆盖范围、方法论、客户构成
- 行业协会 → 统计数据、会员结构、政策接触面

> **设计纪律**：统一抽象只保留"**能不能提供某类信息**"这条主线；一旦某类对象出现新的共性能力，才把它**上提**为通用属性。**不允许**为了"未来可能用到"提前堆字段。

## E. Investment Evaluation：证据驱动的评分

> 用户纠正：**要评分**，但必须是"**可解释、可追溯、证据驱动**"的评分，而不是让 LLM 随手给分。

### E.1 完整链条

```
投资方法论（维度 + 判据 + 权重）
   ↓
多个评价维度
   ↓
每个维度的信息需求
   ↓
Evidence / Claim（支撑）
   ↓
维度评估（Dimension Evaluation）
   ↓
维度得分（Dimension Score）  ← 可解释、可追溯
   ↓
总分（Overall Score）        ← 同时报告覆盖度
   ↓
投资 / 储备决策（Decision）
```

### E.2 每个分数必须能回答"为什么是这个分数"

```
得分（为什么）
   ↓
该维度的评估理由
   ↓
支撑的证据 / 断言
   ↓
原始材料 / 片段
```

- 得分由**方法论定义的判据（锚点）**驱动，不是模型自由发挥；
- 改方法论（新版本）→ 评分口径随之变化，**历史评分仍绑定当时的版本，可比对**。

### E.3 证据不足时：**不可计算**，而不是 0 分

这是本轮的核心纠正之一：

```
技术壁垒：信息不足
   ↓
正确：得分 = 不可计算（evidence insufficient）
错误：得分 = 0 分 / 低分
```

**因此**：
- 维度得分**允许为空**（表示"尚未可评"）；
- 维度状态至少区分：**已评 / 证据不足 / 存在未解冲突 / 不适用**；
- **「不知道」绝不能被折算成「差」**。

### E.4 覆盖度与质量必须分开报告

```
Investment Evaluation
   ├─ 质量面：各维度得分（仅"已评"维度有分）
   ├─ 覆盖度面：N 个维度中，X 个已评、Y 个证据不足、Z 个冲突
   └─ 决策：纳入储备 / 观察 / 暂缓 / **证据不足（不予判断）**
```

**总分规则**：只有当**足够比例**的维度已评时，才给出总分；否则总分标为"证据不足"，并明确列出缺哪些维度。
**决策**：`证据不足` 是**一等决策**，不伪装成"暂缓"或"不看好"。

> 这解决了用户提出的「防止 Information Coverage 与 Investment Quality 被混为一谈」。

## F. Knowledge Evolution：双体系协同（最重要的一节）

### F.1 正向链（行业研究如何产生知识）

```
新资料（研报 / 新闻 / 调研碎片）
   ↓
Evidence（谁在什么材料里说了什么）
   ↓
Claim（断言）
   ↓
按信息槽位汇聚（Pool 更新：新口径与老口径比较）
   ↓
认知更新（Knowledge：支持 / 修正 / 冲突 / 取代，历史永不覆盖）
   ↓
（行业知识体系变厚）
```

### F.2 反向链（行业研究如何反过来改进投资方法）

```
行业研究过程中出现的"方法层面"的信号
   ↓
研究经验（Research Experience：关于"如何研究"的经验）
   ↓
累积成模式（Pattern：不是单例，而是反复出现）
   ↓
方法论修订提案（Methodology Candidate）
   ↓
人工确认（Human Gate）
   ↓
新的方法论版本（Methodology Evolution）→ 下一轮研究更准
```

**关键区分**：
- "AI Agent 行业 2026 年市场规模 500 亿" 是 **行业知识**；
- "对平台型行业，用毛利率判断胜负会失准，应该看网络效应" 是 **研究经验**，它可以推动方法论。

### F.3 什么情况下，一个行业的新发现足以挑战原来的投资方法？

这是用户点名要回答的问题。**五类触发**（我建议的判据）：

| # | 触发 | 说明 | 例子 |
|---|---|---|---|
| **T1** | **预测失准** | 方法论给出的评分/判断，被后续证据证伪 | 技术壁垒评 84，调研发现技术已被替代 |
| **T2** | **关键遗漏** | 方法论未列或低权重的因素，被证据证明是关键驱动（且**跨案例重复**） | 多个平台行业的胜负都由网络效应决定，而 v1 未把它列为维度 |
| **T3** | **重复无效** | 方法论要求的信息，多次研究都无法获得，或证实无判断价值 | v1 要求"未来 3-5 年预期增速"，但该数据在各行业都不可得/不区分结果 |
| **T4** | **口径陷阱** | 方法论假设可比的指标，实际口径不可比 | "市场规模"在不同来源口径差异巨大，直接比较会误判 |
| **T5** | **结构变化** | 行业结构/规则变化使原方法假设失效 | 政策变化后，"牌照壁垒"不再成立 |

**注意**：T1–T5 都是**方法层的信号**，必须与"行业事实"分开记录。**这是两个知识体系不混淆的前提。**

### F.4 防过拟合：单例不改方法论，模式才改

**铁律**：

```
单个行业的新发现 → 只记「研究经验」，不改方法论
        ↓
同类模式反复出现（跨 N 个行业/项目）
        ↓
才生成「方法论修订提案」
        ↓
人工确认（Human Gate）
        ↓
新版本
```

**理由**：一个行业的反例可能只是这个行业的特殊性。若一发现反例就改方法，方法论会被单个案例带偏（过拟合），反而更不懂投资。

**"何时算模式"**由**人工在 Human Gate 判断**（可给系统一个建议信号，但决策权在人）。

### F.5 方法论进化的产出形态

- 新增维度 / 删除维度 / 调整权重 / 增加行业类型的差异化规则 / 修改判据与确认条件 / 新增"该找什么信息"的映射；
- 每次进化都是**新版本**，旧版本保留；
- 历史评估、历史研究都可回溯到当时的方法论版本（"当时我们是按 v1 判断的"）。

## G. Long-term Loop（天查的生命循环）

```
发现行业（材料 / 用户 / 自动搜集）
   ↓
建立研究框架（方法论 → 维度 → 信息需求 → 信息槽位）
   ↓
信息收集（外部数据 / 研报 / 调研）
   ↓
Information Pool（槽位被逐格填充，口径被比较）
   ↓
Knowledge（形成认知，支持/修正/冲突/取代，历史保留）
   ↓
Research Gap（还缺什么 / 哪里冲突）
   ↓
Research Strategy（该去哪找、该问谁）
   ↓
Research Chain → Research Position → Research Target → QuestionTargetFit
   ↓
调研（Diligence Preparation → 实地/访谈）
   ↓
Material → Fragment → Evidence → Claim
   ↓
Knowledge 更新 → Pool 更新
   ↓
Investment Evaluation 更新（维度得分 + 覆盖度 + 决策）
   ↓
发现方法论是否需要修正（T1–T5 信号）
   ↓
Research Experience → Methodology Candidate → Human Gate → 新方法论
   ↓
下一轮行业研究（更快、更准）  ←──────────────┘
```

**两个反馈回路**（这是与"普通研究工具"的根本区别）：
1. **内环**：`研究 → 证据 → 认知 → 缺口 → 研究`（把这个行业研究得更透）；
2. **外环**：`行业研究 → 经验 → 方法论 → 研究`（让"如何研究"变得更好）。

**天查的价值 = 内环的深度 × 外环的进化速度。**

## H. Phase 划分（按业务闭环，不按模块依赖）

> 用户纠正：不要按"数据库对象依赖关系"排序，要按**核心业务闭环 + 两个知识体系共同成长**排序。

### H.1 划分原则

1. **每个 Phase 结束时，必须有一条"用户能感知到的业务闭环"真正跑通**；
2. **外环（方法论进化）不能排到最后**，它必须在第一个完整闭环里就出现（哪怕很薄）；
3. 宁可**闭环窄而完整**，不要**模块全而断开**。

### H.2 Phase 序列

| Phase | 名字 | 要打通的闭环 | 两个知识体系的状态 |
|---|---|---|---|
| **A** | **单行业研究闭环（框架驱动）** | 方法论框架 → 信息需求 → 信息槽位（承载内容）→ 认知 → 缺口 → 评估（含覆盖度） | 投资知识：v1 baseline 可用；行业知识：**从空到有** |
| **B** | **研究策略闭环（去哪找、问谁）** | 缺口 → 观察结构 → 观察位置 → 候选对象 → 适配 → 调研准备 | 行业知识：长出**观察结构**；投资知识：**贡献"为什么要看产业链"** |
| **C** | **调研回填闭环** | 材料 → 片段 → 证据 → 断言 → 认知/Pool/评估更新 | 行业知识：**大幅变厚**；投资知识：**开始接收经验信号** |
| **D** | **双体系协同闭环（外环）** | 经验 → 模式 → 方法论提案 → 人工确认 → 新方法论 | 投资知识：**第一次真正进化** |
| **E** | **自动化与规模化** | 自动搜集/赛道识别 + 外部数据源（Wind）接入 | 两个体系：**吞吐量放大** |
| **F** | **报告与研究规划** | 认知 → 可读报告（投影，非真相）；缺口 → 下一步规划 | 支撑人工使用与决策 |

### H.3 为什么这样排（与上一版 C→D→E→F→G… 的区别）

- **上一版**按数据对象依赖排（先 Chain/Target，再 Diligence，再 Ingestion，评估放很后）。
- **本版**按闭环排：**A 先把"框架驱动研究"这条最内的环打通**（因为没有它，后面全是空中楼阁），**D 把外环接上**——注意 **评估（在 A 里以薄形态出现）和方法论进化（D）都不再被推到最后**。
- **E（自动搜集/Wind）不是第一优先**：它只是"吞吐量"，不是"能力"；在不知道"该怎么研究"之前，自动搜集只会更快地堆出无结构的资料。

> 如果用户希望优先解决"入口自动化"（发现行业），E 可以作为并行支线提前，但它**不替代** A→D 的能力建设。

## I. 自检：这个模型是否真的支持"越研究越懂行业 / 越研究越懂投资"？

| 检验问题 | 模型是否支持 | 靠什么支撑 |
|---|---|---|
| 研究第二个同类行业时，是否更快？ | 支持 | 方法论已有框架（A）+ 观察结构可复用（C） |
| 是否越来越懂**这个**行业？ | 支持 | 信息槽位持续填充（B）+ 认知历史累积（F.1） |
| 是否越来越懂**如何研究**？ | 支持 | 外环：经验 → 模式 → 方法论（F.2–F.4） |
| 新信息和老信息冲突时会不会丢历史？ | 支持 | 槽位内条目并列（B.3）+ 认知四态不覆盖（F.1） |
| 方法论会不会被单个案例带偏？ | 支持 | 单例只记经验，模式才改方法（F.4）+ 人工闸门 |
| "不知道"会不会被当成"差"？ | 支持 | 得分可空 + 覆盖度与质量分离（E.3/E.4） |
| 调研对象只有企业时会不会失真？ | 支持 | ResearchTarget 泛化为"信息源"（D） |
| 找错调研对象会不会静默？ | 支持 | QuestionTargetFit + Fallback 显式标注（C.3/C.4） |
| 用户会不会被迫理解内部模型？ | 需 UX 层保证 | NL 进 / NL 出（Phase F 之前就要维持） |
| 报告会不会变成"第二套真相"？ | 支持 | 报告是投影（§G 的收尾），真相永远是断言/证据 |

**唯一需要警惕的地方**：外环（F）如果做得太"自动"，会退化成"模型自学改方法论"，直接违反铁律。**必须始终是"经验 → 提案 → 人批准"**。

## 结语

天查的成败不取决于表建了多少、工具接了多少，而取决于**两个问题**：

1. 它是不是真的能**把一个行业研究透**（内环）；
2. 它是不是真的能**从每次研究里学到"该怎么研究"**（外环）。

本模型的所有设计都服务于这两点。**请确认 §A–§I 的方向是否正确**（尤其是：信息池承载内容、要评分但可空、调研对象泛化、外环不后置、Phase 按闭环排）。

确认后，我再进入代码/领域模型设计。
